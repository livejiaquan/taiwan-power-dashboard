# 使用者研究（2026-10-22）

這份文件從軟體工程的角度回答「誰會用這個頁面、拿它做什麼、它必須達到什麼品質」，作為介面取捨的依據。沒有做訪談；推論來自產品定位（[`PRODUCT.md`](PRODUCT.md)）、台電資料的實際使用情境、同類產品的設計（[`design-research.md`](design-research.md)），以及可查得的流量統計。凡是推估都會標明。

## 使用情境

1. **傍晚尖峰前的確認**（阿哲）：18:30 在捷運上收到「今晚可能限電」的轉傳，點開連結，想在 5 秒內知道台電現在亮什麼燈。
2. **寫稿取數**（Mia）：14:00 開桌機，要寫「今日尖峰備轉率」與「再生能源占比」，需要確切數字、資料時間、可貼進稿件的圖或表。
3. **比較與追蹤**（Ken）：想看最近十天備轉率的走勢與未來一週預測，以及哪些大型機組在檢修。
4. **評估作者**（Sam）：花 1–2 分鐘掃過首屏、切深色模式、縮到手機寬度、點開原始碼與文件。

## 前三項任務（依頻率與重要性）

| # | 任務 | 成功標準 | 頁面上的答案 |
| --- | --- | --- | --- |
| 1 | 判斷「現在電夠不夠」 | 5 秒內說出燈號與備轉率，且知道資料是否即時 | 時效細帶 → 燈號板 → 大字備轉率，三者都在手機首屏 |
| 2 | 確認資料新不新、可不可以引用 | 看到兩份來源各自的時間與「幾分鐘前」；過期時有替代出路 | 時效細帶永遠在數字之前；過期時「看台電官網最新數字」 |
| 3 | 了解電從哪裡來、今天怎麼變化 | 能說出前三大燃料占比與今日尖峰時段 | 「此刻的電網」面板、發電結構清單、今日曲線與備轉趨勢（附表格與 CSV） |

次要任務：查單一機組（搜尋、篩選）、切換萬瓩／MW、下載資料、理解名詞。

## 非功能需求

| 類別 | 需求 | 驗證方式 |
| --- | --- | --- |
| 正確性 | 只顯示通過驗證的台電資料；不以 sample、建置時間或瀏覽器時間製造即時感 | `node --test` 資料信任測試（[`DATA_TRUST_CONTRACT.md`](DATA_TRUST_CONTRACT.md)） |
| 時效透明 | live／delayed／stale／unavailable 依來源時間判定，每 15 秒重算，「非即時」標示在所有主要指標之前 | Playwright e2e（四種狀態） |
| 效能 | 行動版 Lighthouse Performance ≥ 90、首屏不依賴圖表函式庫、CLS ≈ 0 | Lighthouse（見 PR 紀錄） |
| 無障礙 | WCAG 2.1 AA：文字對比 ≥ 4.5:1、狀態不只靠顏色、觸控目標 ≥ 44px、可暫停自動更新、每張圖有表格替代 | axe（CI）、對比計算、手動檢查 |
| 相容 | 320px 無橫向捲動；淺色／深色；`prefers-reduced-motion` | e2e、手動 |
| 隱私 | 不載入第三方追蹤或字型服務，所有請求同源 | e2e「不對外請求」測試 |
| 可維運 | GitHub Pages 靜態部署；排程失敗時頁面自動把舊資料標成延遲／過期 | Pages workflow、e2e |

## 裝置評估

- **外部數據**：StatCounter 2026 年 9 月台灣網頁流量，手機 58.05%、桌機 38.58%、平板 3.37%（[來源](https://gs.statcounter.com/platform-market-share/desktop-mobile-tablet/taiwan)，2026-10-22 查詢）。
- **本站推估（未經實測，本站沒有流量分析）**：兩種流量來源方向相反。供電新聞與社群轉傳帶來的民眾，手機比例應高於全台平均，推估 70% 以上；GitHub 作品集帶來的審閱者以桌機為主，推估 80% 以上。
- **結論：兩邊都重要，兩邊都做到精緻。** 手機是一般民眾的主力，首屏必須在 390px 寬度直接看到燈號與備轉率，控制項要好按；桌機是作品集審閱者與記者的主力，要善用寬度（燈號板與答案左右並排、圖表與表格完整）。平板沿用桌機版面，不另外設計。

## 這份研究改變了什麼

- 手機首屏順序固定為：時效 → 燈號＋備轉率 → 燈號板，其他內容往下排。
- 首屏以外的內容（圖表、機組、說明）延後載入，讓手機在慢速網路下先看到答案。
- 所有控制項在觸控裝置上至少 44px；桌機滑鼠操作維持較緊湊的尺寸。
- 每張圖保留表格與 CSV，給記者與研究者引用。
